# Добавление фичи

Задача: $ARGUMENTS

Если задача выше пустая или из неё непонятно, что должно получиться, спроси одним
вопросом, что именно сделать, и дальше не иди.

## 1. Контекст проекта

- Прочитай итоговые доклады `pipeline/*/report.md` — там решения и допущения прошлых
  задач. Остальные файлы задачи открывай, только если доклада не хватает.
  Выжимки сейчас не создавай: позже их будет вести отдельный агент `documentator` в своей
  папке в корне проекта, и тогда этот шаг будет читать её вместо `pipeline/`.
- Посмотри `git status`: незакоммиченные изменения пользователя не трогай и не
  смешивай со своими. Если они затрагивают те же файлы, что и фича, предупреди.
- Найди, где живёт похожий код, и повторяй его устройство: имена, структуру файлов,
  способ подключения. Фича, написанная «как у соседей», проще для ревью и поддержки.

## 2. Реализация

- Новых зависимостей не добавляй: ни composer, ни npm, ни CDN. Нужное пиши сам на
  том, что уже есть. Если без библиотеки фичу не сделать разумно, остановись и
  спроси, а не ставь её молча.
- Фронтенд (`resources/css`, `resources/js`, `resources/views`) подчиняется
  `.claude/rules/ui.md` — прочитай его перед правками. Самые частые промахи: цвет
  литералом вместо переменной в `:root`, `px` в размерах, стили или скрипты внутри
  шаблона, кнопка без `:hover` или с другой высотой.
- Состояние, которое пользователь мог накопить (рекорды и настройки в
  `localStorage`, данные в БД), сохраняй совместимым: старое значение должно
  читаться, мусорное — не ломать страницу.
- Добавь или дополни feature-тест в `tests/Feature/` на то, что можно проверить на
  стороне сервера (страница отдаёт 200, нужная разметка на месте).

## 3. Проверка

Сначала автоматические проверки:

```bash
npm run build                                   # без этого браузер покажет старую версию
docker compose exec -T app php artisan test     # все тесты, не только новый
```

Потом в браузере (Claude in Chrome): открой страницу с фичей на
`http://localhost:8000` и пройди её как пользователь — настоящими кликами и
клавишами, а не только через JS. Проверь:

- основной сценарий и пару граничных (повтор, неверное значение, перезагрузка);
- консоль без ошибок;
- светлую и тёмную тему, если менялся вид, — тёмную в Chrome, светлую через headless
  Chrome с `--blink-settings=preferredColorScheme=1`.

Если по ходу проверки что-то сломалось — чини и проверяй заново, это часть фичи.
За собой убери: закрой свою вкладку, верни данные пользователя (`localStorage` и
т. п.) в то состояние, в котором они были до проверки.

## 4. Отчёт

Пиши тепло и по-деловому: начни с того, что теперь умеет проект, и порадуйся
результату вместе с пользователем. Позитивный тон — не повод приукрашивать: что не
проверено или работает с оговорками, скажи прямо, иначе пользователь узнает об этом
в самый неудобный момент.

Состав отчёта:

- что появилось — с точки зрения пользователя;
- как проверял и что увидел;
- изменённые файлы, по строке на каждый;
- что не проверено и какие решения ты принял сам (их пользователь может захотеть
  поменять).

## 5. Без коммита

Изменения не коммить и не пушь: пользователь сначала посмотрит сам. В конце отчёта
скажи, что всё готово к коммиту, когда он решит.
